# devkit

Shared tooling for the Dustin Edwards repositories, public so private repositories can use it.

- `default.json`: the Renovate policy. Each repository's `renovate.json` extends it; each setting's reason is in its description.
- `.github/workflows/`: reusable workflows, each called, never run on its own. A caller pins a full 40-character devkit sha, and `scripts/check-callers.mjs` (run by the caller on its own workflow files) fails on a branch, a tag or `secrets: inherit`. `examples/` holds the shape of each caller.
  - `ai-author.yml`: refuses an AI attribution trailer on new commits, and on a pull request a commit authored or committed as Claude (`devkit-check-trailers`). It installs devkit from the tag in the caller's package.json, or from the `devkit` input.
  - `pr-footer.yml`: removes the "Generated by Claude Code" footer from pull request descriptions. The script is inline, so a caller needs only the sha.
  - `no-bloat.yml`: the Knip, jscpd and test count ratchet (`devkit-no-bloat`), and on a pull request the lines it adds and removes in the job summary. Public repositories call it on every pull request; private ones weekly.
  - `worker-size.yml`: the Worker bundle size budget (`devkit-worker-size`).
  - `worker-deploy.yml`: deploy, verify and roll back a Cloudflare Worker. See "The shared deploy".
  - `restore-drill.yml`: the weekly restore drill of a site's nightly D1 dump. See "The restore drill".
  - `code-map.yml`: the code map for the explorer at capsid.dustinedwards.info. See "The code map".
  - `workflow-audit.yml`: actionlint (with shellcheck) and zizmor at its default persona on the caller's workflows and actions. Any actionlint finding fails, and any zizmor finding at `min-severity` (default `medium`) or above; each is an annotation on its line. The tools are release files at exact versions (actionlint 1.7.12, shellcheck 0.11.0, zizmor 1.31.1), checked against their sha256. Exceptions are the tools' own files, each with its reason: `.github/actionlint.yaml` (`paths`, `ignore`) and `.github/zizmor.yml` (`rules`, `ignore`). devkit's own `.github/actionlint.yaml` accepts `job.workflow_sha`, which GitHub documents and actionlint 1.7.12 does not know yet.
  - `dependencies.yml`: known vulnerabilities, found by OSV-Scanner 2.7.0 (checked against its sha256) in every lockfile in the repository, nested ones included (a repository with none passes). On a pull request or a merge queue entry it also scans the base commit and fails only on a vulnerability the change adds, which is OSV-Scanner's documented pull request mode; on a push or a schedule it fails on every known vulnerability. It needs no repository setting and works the same in a private repository, where GitHub's dependency review needs paid Code Security. `osv-scanner.toml` at the root (`[[IgnoredVulns]]` with `id`, `reason`, `ignoreUntil`) holds exceptions for every lockfile. The caller (`examples/dependencies-caller.yml`) adds a daily schedule, which finds an advisory published after a merge.
  - `release.yml`: a package repository's release. When `package.json`'s version on the default branch has no `v<version>` tag, it tags that commit and publishes a GitHub release with the version's CHANGELOG section (GitHub's generated notes when there is none), so merging the version bump is the release and nobody pushes a tag by hand. Its `created` output starts `bump-consumers.yml` (`examples/release-caller.yml`). devkit releases itself with it (`release-self.yml`).
  - `bump-consumers.yml`: a package repository calls it on a tag push; it starts a Renovate run in every repository whose `package.json` depends on that package. It needs the `RENOVATE_TRIGGER_TOKEN` secret described in its header.
- `testing/` and `bin/`: the package (`@dustinedwards/devkit`): shared test helpers and shared checks. See below.
- `test/`: CI runs these (`npm test`).

## The shared checks

Bins in the package, so a check runs the same locally (`npx <bin>`) as in the workflow that calls it. The workflow runs the bin from the caller's own install, so the caller lists `@dustinedwards/devkit` in its devDependencies at a tag.

- `devkit-no-bloat`: Knip, jscpd and the tests, each count compared with the baseline in the repository's `.no-bloat.json`. A count above its baseline fails (exit 1, an `::error::` line each); a count at or below passes, and one that went down is named, with the way to lower the baseline: `npx devkit-no-bloat --write-baseline`, then commit `.no-bloat.json`. A deliberate raise is the same command, in a reviewed change; the pull request that adds a test raises the baseline in the same diff. Gated: each Knip heading, jscpd's clones and duplicated lines (its percentage is shown, not gated, since deleting code that is not duplicated raises it), and the test files and test cases. Tests are counted statically, never run: the files matching `tests.files` (default `**/*.{test,spec}.{js,mjs,cjs,jsx,ts,mts,cts,tsx}`), and in them each `test(` or `it(` call of node:test, vitest or Playwright, outside comments and strings (`describe`, hooks and Playwright's `test.skip(condition)` are not cases; a case made in a loop counts once). The share of source lines that are comment lines is recorded too; a rise of more than `comments.tolerance` points (default 1) with more comment lines than the baseline is a warning, or a failure with `comments.fail: true`, so deleting code alone never trips it. A tool that cannot run fails, naming its error, and so does a config that is not JSON, Knip output with no heading it reads, a jscpd run that read no files, and a baseline entry that no run in the config measures. `--lines-from <rev>` adds the lines added and removed since the merge base with `<rev>`, as code, tests, comments, docs and other, blank lines not counted; `no-bloat.yml` passes it on a pull request, so the job summary shows them. Tools run from `node_modules/.bin` when installed, otherwise through npx at the config's `tools` (default `knip@6`, `jscpd@4`). The config's fields are in the header of `bin/no-bloat.mjs`. `--warn-only` (the workflow's `warn-only: true`) makes it a report: the same table, every error a `::warning::` line, exit 0, for a repository that watches the numbers without gating on them.
- `devkit-conformance`: the official MCP conformance suite (`@modelcontextprotocol/conformance`, from the repository's own install) against a Worker's protocol layer and its authorization server under `wrangler dev`, per era, from `.conformance.json`. A scenario with a recorded pass count must hold it exactly (fewer is a regression, more means tighten the baseline); one without must pass every check. Then it pins what the suite treats as optional: CIMD advertised, `/register` at the auth origin registering an allowlisted callback (201, no token) and refusing any other (400 `invalid_redirect_uri`), and `/mcp` without a token answering 401 with a `resource_metadata` challenge (`auth.resourceMetadata: false` waives the challenge for a server that does not advertise it yet). Local only, never on Actions. The config's fields are in the header of `bin/conformance.mjs`.
- `devkit-bootstrap`: the postinstall. Copies each `wrangler*.jsonc.example` at the root to its real name when that is missing, never overwriting, then runs `wrangler types` with stdin detached, so wrangler's hidden skills prompt cannot hang `npm install`. Arguments after `--` go to `wrangler types`; `--types-only` skips the copy (for `typecheck`); `--check` fails when a `package.json` script runs a bare `wrangler types`.
- `devkit-worker-size`: runs `wrangler deploy --dry-run` and fails when its "Total Upload" (raw or gzip, the size Cloudflare counts) is over the budget in the repository's `.worker-size.json`: `{ "raw_kib": 1700, "gzip_kib": 400 }`, with optional `args` for the dry run and `wrangler` (npx spec when wrangler is not installed, default `wrangler@4`). Cloudflare's upload limits are far higher; the budget is about startup, which must finish inside 1 s. No budget file, a failed dry run or no Total Upload line fails. The workflow's `prepare` input gives the dry run a config (`cp wrangler.jsonc.example wrangler.jsonc`, or a build) and `working-directory` names where it lives. No secret is needed.
- `devkit-route-weight`: the gzip JS and CSS a first visit to each route downloads, read from a React Router client build's manifest (`build/client`, or `--client <dir>`): the client entry, then root down to the route, each file counted once, gzipped at level 9. With the optional `.route-weight.json`, a route over `budget_bytes`, or grown past its baseline by more than `growth.ratio` and `growth.bytes` (default 0.05 and 1024), is a `::warning::` line and the run passes; with `"enforce": true` it is an `::error::` and the run fails, and the config must set `budget_bytes`. `npx devkit-route-weight --write-baseline` records the baseline; `linked_css: true` also counts a stylesheet the JS links by URL (`app.css?url`). No build fails. The config's fields are in the header of `bin/route-weight.mjs`.
- `devkit-mutation-report`: merges a StrykerJS run's JSON reports (`--dir`, default `reports/mutation`) and prints the mutation score and the pruning candidates (zero-kill and covered-by-others tests), never deleting anything. `--protected <regex>` is the repository's keep rule, matched against each test's file and name; `--table` adds a per-file table and `--json <file>` writes the kill matrix.
- `devkit-family`: keeps a repository in step with the family. It fails on a shared package, devkit workflow or ai-author `devkit:` input pinned behind its newest release tag or to a raw commit; on a local copy of something a shared package exports (a definition with its name or a known alias, or text only its builder writes, such as `User-agent:`, `<urlset`, an inline `type="speculationrules"`, a direct `IMAGES.input(` resize, an island loader's `[data-island]` query, JSON-LD or head tags by hand, a hex or base64url encoder, a constant-time compare, a pre-paint theme script, or a security header set in a static `_headers` file); on a direct dependency on a library a package wraps (marked, remark, mermaid, sanitize-html, jose); on a family feature the app's kind needs and does not import; on a site setting its own value for one of Capsomer's tokens for the whole page (`:root`, `html` or `body`), such as `--page-max`, `--radius-m` or `--text`, which belongs in Capsomer or its site layer; on British spelling (codespell's en-GB to en-US list, through `pipx` when codespell is not installed); on a devkit workflow the repository's kinds need that no workflow calls (every repository: `ai-author`, `pr-footer`, `family`, `workflow-audit` and `dependencies`; an app of kind `site`, `private` or `worker` with a wrangler config: `worker-size` and, as a lasting warning, `worker-deploy`; a public repository with JavaScript or TypeScript: `no-bloat`; a shared package: `bump-consumers`), where CI running the bin itself, directly or through a package script, counts, and several apps need the union of their kinds'; and on a test fake devkit already ships (a GitHub API fake of contents or git data routes, an Access key pair with the key set it serves, a fetch that refuses every URL, a list of `DELETE FROM`s), naming `./github`, `./access`, `./network` or `./d1`: the one check that reads test files. Whether a repository is public comes from the Actions event, so locally `no-bloat` is only a warning. The kinds are `site` (a public Worker site), `static` (a public static site), `private` (behind Cloudflare Access), `worker` (an MCP or API Worker) and `package`, set per directory in `.family.json`, which also holds each exception with its reason (`"waive": { "workflow:<name>": "why" }` for a workflow). An unknown key or kind in `.family.json` stops the check (exit 2, naming the valid ones), and so does a `--from` directory missing a package; locally, a package not in `node_modules` is named in a warning, since copies of its exports were not checked. An exception that excused nothing in the run (`copies`, `waive`, `libraries`, `tokens`, `spelling.ignore`, `spelling.contracts`) is a warning naming it, judged only when every package was read. Exit 2 means the check could not run. On a Renovate branch a stale pin is a warning, so one bump never waits on another. A new rule arrives as a warning (`::warning::`, exit 0) for one release and fails from the next, so the sites can move first: each rule's `failsFrom` names the release, compared with devkit's own `package.json` version, so releasing it is the flip. Three heuristic features (an accessibility test, noindex on admin and login routes, a feed's alternate link), `worker-deploy` and a stale exception stay warnings. `--fix-spelling` rewrites the British spellings in place; a line ending in a `codespell:ignore` comment is a data contract it leaves. `devkit-family list` prints every family feature and every package's exports; `shared-list.yml` publishes that list hourly to https://github.com/DrDustinEdwards/devkit/blob/shared-list/SHARED.md. The config's fields are in the header of `bin/family.mjs`. A repository runs it by calling `family.yml` (`examples/family-caller.yml`), which needs nothing installed: it checks out devkit at the pinned commit and reads each package at its newest tag. Spelling also reads each part of a camelCase or CONSTANT_CASE name; the fix rewrites whole words only, so an exported name is renamed by hand with the old one kept as an alias.
- `devkit-check-trailers`: with no arguments it reads the range from the GitHub event (`EVENT`, `PR_BASE`, `PR_HEAD`, `PUSH_BEFORE`, `PUSH_AFTER`, set by `ai-author.yml`), and for `merge_group` the group's base and head from the event payload; locally, `npx devkit-check-trailers <base> <head> [--authors]`. Schedule, `workflow_dispatch` and `repository_dispatch` add no commits and pass. Exit 1 names each commit and how to fix it; exit 2 means it could not read the commits or does not know the event, which is a failure, not a pass.

- `devkit-live`: the completeness scoreboard. See "The scoreboard".
- `devkit-ops-audit`: running and recovery on a live site, area 8's scoreboard check: `devkit-ops-audit --origin <origin> [--from <host>] [--health-path /health] [--repo owner/name] [--branch <branch>] [--drill-workflow <file>]`. It reads `/health` (H1: 2xx or 503, `application/health+json` or `application/json`, `Cache-Control: no-store`, `X-Robots-Tag: noindex`; H2: site-runtime's shape, `status` pass, warn or fail, `ok`, `time` and `checks`; H3: 503 for fail and only for fail; H4: `sha` of 7 to 40 hex characters; B1: a `backup` under 26 hours old with no warning; C2: a `cron` check that passes) and a random missing path (N1: a 404, never a redirect or a 200; N6: an HTML page). With `--repo`, `sha` must be the branch head (the default branch unless `--branch`; a head under 30 minutes old is a warning, a deploy may be in flight), and with `--drill-workflow`, that workflow's newest completed run on the branch must be a success under 8 days old (R1). GitHub is read without a token, or with `GITHUB_TOKEN`; a repository it cannot read is a warning. A health route elsewhere is named with `--health-path`; nothing falls back to it silently. Each finding is `::error title=<item>::<proof URL> <detail>` (or `::warning`), after one plain line per check saying what it read; exit 0 with no errors, 1 with any, 2 when the site answered nothing at all.

Per-repository measurements (capsomer's page weight, capsid's dashboard size budget) stay in the repository.

## The scoreboard

One board shows each of the 12 areas of the shared code against the package and every live site, at https://github.com/DrDustinEdwards/devkit/blob/scoreboard/SCOREBOARD.md. It is filled only from live checks and verifiers' verdicts, never from the thread that built an area.

- `live/sites.json`: every live site, its kind (`site`, `static`, `worker`), its production `origin`, and `from` where it is served until its domain moves.
- `live/areas.json`: each area, the thread that builds it, and its checks. A check is a bin in a shared package, installed at the newest release tag (or `ref`), run as `<bin> --origin <origin> [--from <from>]`. It prints each finding as an annotation, `::error title=<item>::<proof URL> <detail>`, and exits 0 with no errors, 1 with errors, anything else when it could not run: the contract `prelum-audit` keeps. `kinds` names the site kinds it applies to; an area's `skip` names a site it does not apply to, and why.
- `live/verdicts/area-<n>.json`: a verifier's verdict, per site and for the `package`, `complete`, `partial` or `missing`, with evidence links. The verifier must not be the area's builder, and a complete cell needs evidence: `devkit-live lint` fails CI otherwise.

A cell is complete only when its checks pass in the newest run, the verifier signed it complete, and no run after the verdict failed; a failure after a verdict voids it until a fresh verifier signs again. Checks passing without a verdict is partial; no check, a failing one or one that could not run is missing. The job is finished when every cell is complete and every site cell has passed seven daily runs in a row. Lines added and removed per area are the merged pull requests labeled `completeness-area-<n>`, read with the `LIVE_GITHUB_TOKEN` secret (without it, public repositories only).

`live.yml` runs it daily, fails when any check fails or could not run, and keeps 60 days of runs on the branch. Locally: `node bin/live.mjs run --out run.json --areas 1 --sites capsomer`, then `node bin/live.mjs board --runs <dir of runs> --out board.json --md SCOREBOARD.md`.

## The shared deploy

`.github/workflows/worker-deploy.yml` deploys a Cloudflare Worker, checks it live, and rolls it back when the check refuses it. It is capsid's `deploy` and `live gate` jobs and `scripts/rollback-guard.mjs`, so every Worker site gets what capsid has. A caller (`examples/worker-deploy-caller.yml`) calls it on a push to its default branch, after its own checks, pinned to a full devkit sha, with a concurrency group that never cancels a deploy in flight.

Two jobs:

- `deploy` checks out, installs, runs the caller's pre-deploy guard, runs `wrangler deploy` with the wrangler version pinned in the file, and publishes the run attempt it shipped in. Never on a pull request.
- `live gate` polls the health URL (40 reads, 3 seconds apart) until its JSON `sha` is this run's commit, then runs the verify command. Exit 0 passes. Exit 1 is a refusal, and only a refusal runs "Roll back the deploy this run shipped": the rollback guard rolls back only when what is live is this run's commit (or /health is unreadable and the deploy ran in this same attempt), runs `wrangler rollback`, and reads /health until the sha moves. Exit 3, or a /health that never answered, is "could not run": the job fails and nothing rolls back.

capsid's watcher reads the job name `live gate`, the step name, and the step's three `::error::` sentences ("rolled back: was ...", "not rolling back. ...", "the rollback did not take effect: ...") to write `deploy_outcomes`, and the step summary carries `rollback_from=` and `rollback_to=`. `test/worker-deploy-workflow.test.mjs` fails on a change to any of them.

Inputs:

| Input | Required | Default | What it is |
|---|---|---|---|
| `worker-name` | yes | | The Worker's name, for `wrangler deploy --name` and `wrangler rollback --name`. |
| `health-url` | yes | | The live health route. It must answer JSON whose `sha` is the deployed commit (abbreviated to 7 or more hex characters is fine). |
| `verify-command` | yes | | The live checks, run in the working directory with `EXPECT_SHA` and `HEALTH_URL` set and no install. 0 passes, 1 refuses, 3 could not run. It gets no Cloudflare secret. |
| `node-version-file` | no | `.nvmrc` | As `actions/setup-node` reads it, from the repository root. |
| `working-directory` | no | `.` | Where the Worker and its `wrangler` config live. |
| `install` | no | `npm ci` | The deploy job's install. |
| `pre-deploy` | no | none | The caller's guards before the deploy (a migration check, a config rebuild, a build), run with the Cloudflare secrets. A failure stops the deploy. |
| `sha-var` | no | none | When set, the deploy passes `--var <name>:<this run's commit>`, so the Worker can report it on /health. |
| `d1-database` | no | none | The D1 database's name. When set, the deploy job reads its Time Travel bookmark (`wrangler d1 time-travel info <db> --json`) before the pre-deploy guard, and writes it, the time and the undo command to the step summary and to the outputs `d1-bookmark` and `d1-bookmark-time`. A bookmark it cannot read stops the deploy. The token then also needs D1: Read. |

Secrets, passed by name (`secrets: inherit` is refused by `check-callers.mjs`): `CLOUDFLARE_API_TOKEN`, a token that can deploy and roll back the Worker (Workers Scripts: Edit), and `CLOUDFLARE_ACCOUNT_ID`. Both are required, and a missing one fails the deploy loudly rather than skipping it.

The limits. Cloudflare's rollback swaps the Worker's code and bindings only. It is refused when D1 or KV resources changed between the two versions, and it never undoes a D1 migration (Cloudflare Docs, "Rollbacks"). A deploy that ran a migration is not made safe by this workflow: keep migrations a separate, human step, and check them in `pre-deploy`. Data recovery is D1 Time Travel, by hand: with `d1-database` set, the run's summary holds the bookmark from before the guard and the one command that goes back to it, `npx wrangler d1 time-travel restore <db> --bookmark=<bookmark>`. The rollback goes to the previous version, whatever that is; the guard is what stops a rerun from moving production onto the refused commit.

The guard is inlined into the workflow so a caller's one pinned sha fixes both. After an edit to `scripts/rollback-guard.mjs`, run `node scripts/inline-rollback-guard.mjs`; the test fails while the two differ.

## The restore drill

`.github/workflows/restore-drill.yml` proves a site's nightly D1 dump restores. Every site with a D1 database calls it weekly (`examples/restore-drill-caller.yml`): it runs `npx github:DrDustinEdwards/d1-dump#<d1-dump-ref> drill --bucket <bucket> --backend sqlite`, which downloads the newest complete run from the backups bucket through the R2 REST API, restores it into a scratch SQLite file and checks the copy (d1-dump README, "Restore drill"). Exit 1 is a dump the drill refused, 3 a drill that could not run; both fail the job, and the output goes to the step summary. `devkit-ops-audit --repo <repo> --drill-workflow <the caller's file>` reads the newest run (R1).

Inputs: `bucket` (required), `d1-dump-ref` (required, a d1-dump release tag, so a d1-dump release reaches the drill through a reviewed change) and `node-version` (default 24). Secrets, by name: `CLOUDFLARE_API_TOKEN` (R2: Read on the bucket is enough; the sqlite backend creates no database) and `CLOUDFLARE_ACCOUNT_ID`.

## The code map

`.github/workflows/code-map.yml` runs on a push to a public repository's default branch and replaces `code-map.json` on that repository's orphan `code-map` branch. Capsid reads it there and the explorer draws it. The script, `scripts/code-map.mjs`, is inline in the workflow, so a caller pins one sha and needs no release (`examples/code-map-caller.yml`).

It reads the code through the caller's own TypeScript, so there is no new dependency: imports are resolved with the caller's compiler options, and cyclomatic complexity is counted on the syntax tree (one, plus each if, loop, case, catch, `?:`, `&&`, `||` and `??` in a function's own body). Coverage is the istanbul JSON Vitest writes (`--coverage.reporter=json`) or the lcov file of `node --test --experimental-test-coverage --test-reporter=lcov`, and a Stryker `mutation.json` adds mutants and a mutation score; both are mapped onto the innermost function holding each statement or mutant. CRAP is CC² × (1 − coverage)³ + CC. A number nobody measured is null, never 0.

Mutation runs only when `mutation-command` is given, which a caller does on a weekly schedule: that run's Stryker reports (`mutation-file`, a glob for one report per chunk) are kept as `mutation.json` on the `code-map` branch beside the map. Every other run reads that file back and, from the source each report holds, carries a function's numbers forward only while its lines are unchanged; a function that changed or is new is `stale: true` with no numbers, and the map names the run as `mutated: {sha, date}`.

Inputs: `coverage-command` (empty for no coverage), `coverage-file`, `mutation-command`, `mutation-artifacts` (for a caller whose Stryker run is a matrix of earlier jobs: the pattern of the artifacts holding the reports, downloaded from that run into `mutation-artifacts/<artifact>/`), `mutation-file`, `tsconfig` (a repository without one is read as plain JavaScript modules), `include` (path prefixes to map, separated by spaces, default `src/`; `.` for every folder), `exclude` (prefixes to leave out), `install` (must install `typescript`; a JavaScript repository can add it with `npm i --no-save typescript`), `npm-cache` (false for a repository with no `package-lock.json`) and `node-version-file`. Locally: `node scripts/code-map.mjs --out code-map.json [--coverage coverage/coverage-final.json]` from the repository's root.

devkit maps itself the same way (`code-map-self.yml`), and once a week mutation-tests its own checks: `node stryker.config.mjs` runs Stryker 10.1.1 (through npx, so nothing is installed) once per module in `bin/` and `scripts/`, each against its own test file, and fails when a module's score falls below its bar in `stryker.config.mjs` (`thresholds.break`). One module: `MODULE=family npx --package @stryker-mutator/core@10.1.1 stryker run`, report in `reports/mutation/family.json`.

## The shared test helpers

Test code that more than one repository needs, written once here. Installed by tag:

    "@dustinedwards/devkit": "github:DrDustinEdwards/devkit#v0.8.0"

Only `testing/`, `vite/`, `bin/` and this README are in the package. No dependencies and no test framework: they run in node and in workerd.

- `@dustinedwards/devkit/github`: `stubGitHub({ owner, repo, branch, files, token })`, a fake of the GitHub contents and Git Data API at the outbound fetch. An unknown host or route throws, blob shas are real and tree and commit shas are 40 hex digits, a tree applies only when the ref moves, and the ref moves only forward: a commit whose parents do not reach the head answers 422 `Update is not a fast forward` unless `force`. Writes answer 201, `base_tree` and `?ref=` are honored, and a `Request` is read for its method, headers and body. With `token` the repository is private: no token answers 404 and another one 401. `failNext` plants 500s and `history` plants the commit listing. `install: false` hands back the fake as `fetch` instead of installing it globally. `gitBlobSha` and `versionOf` come with it.
- `@dustinedwards/devkit/network`: `refuseNetwork({ hint })`, the global fetch that throws naming the URL, and `installFetch`, the swap under it and under the GitHub fake. Each returns its restore.

- `@dustinedwards/devkit/d1`: `resetDb(db, { keep })`, which empties every table `sqlite_master` lists in one batch, so a table a migration adds is cleared without anyone adding it to a list. A full-text table is cleared through itself and its shadow tables are left to it; foreign keys are checked at commit, so table order does not matter; `d1_migrations`, SQLite's and D1's own tables are never touched. It returns the tables it cleared.
- `@dustinedwards/devkit/access`: `await stubAccess({ issuer, audience, email, authorizationUrl })`, a fake of Cloudflare Access for SaaS for one sign-in. The token endpoint answers a POST with `grant_type=authorization_code`, the authorization URL's `redirect_uri` and a `code_verifier` matching its `code_challenge`, and refuses anything else with a 400 as RFC 6749 words it; it answers an RS256 ID token carrying the issuer, the audience, `sub`, the email and the nonce from the authorization URL. `token(extra)` signs an application token (what a test sends as `Cf-Access-Jwt-Assertion`, with `jwksUrl` set to the team's `/cdn-cgi/access/certs`) with the claims Cloudflare documents: `aud` an array, `email`, `exp`, `iat`, `nbf`, `iss`, `type`, `identity_nonce`, `sub` and `country`. `claims` adds to every token. The JWKS serves two keys, the current and the previous, as `keys`, `public_cert` and `public_certs`, and `rotate()` moves to a new key the way Access does; `jwk` is the current one. `tokenRequests` holds what the token endpoint received. An unknown URL throws unless `fallback` answers it.

`test/testing-contract.test.mjs` holds both fakes to what GitHub and Cloudflare publish: each served operation's success status and response field names from GitHub's OpenAPI description, and the application token's claims and the certs endpoint's fields from Cloudflare's docs, extracted into `test/fixtures/fakes-contract.json` by `npm run contract` (`scripts/fakes-contract.mjs`, at a pinned commit of `github/rest-api-description`). Run it again when either source moves.

- `@dustinedwards/devkit/vite/site-script`: `siteScript({ entry, islands, toolbar })`, a Vite plugin for a site that sends no framework to the browser. It bundles `entry` (default `app/site.ts`; `false` for an app with its own client script) into one minified classic script at `/site.js`, and each file in `islands` (default `app/islands/`) into an ES module, so a CSP's `script-src 'self'` covers them. A build bundles every island in one pass, so code two islands import is one shared chunk under `/islands/chunks/`, fetched once and still same-origin, and names every file by its content (`/islands/<name>-<hash>.js`), so `/islands/*` can be cached immutable; the built `/site.js` carries the map `startIslands` reads. `vite dev` serves each island whole, per request, at `/islands/<name>.js`. A server-rendered app reads the same map from `virtual:islands`, with each island's size:

  ```ts
  import { ISLAND_GZIP_BYTES, ISLAND_URLS } from "virtual:islands";
  // ISLAND_URLS.gallery: "/islands/gallery-Bx3k9Q2a.js" ("/islands/gallery.js" in vite dev)
  // ISLAND_GZIP_BYTES.gallery: gzip -9 bytes of the island and the chunks it imports, each once
  ```

  A TypeScript site declares it in an ambient `.d.ts` naming its islands: `declare module "virtual:islands" { export const ISLAND_URLS: Readonly<Record<"gallery", string>>; export const ISLAND_GZIP_BYTES: Readonly<Record<"gallery", number>>; }`. In `vite dev`, `/site.js` also loads the dev toolbar unless `toolbar: false`. Vite comes from the site; this package still has no dependencies.
- `@dustinedwards/devkit/islands`: `startIslands({ root, load })`, Astro's client directives for those islands. An element names its island and when it starts, and the page's HTML works before it does:

  ```html
  <div data-island="gallery" data-client="visible" data-props='{"start":2}'>...</div>
  ```

  `data-client` is `load` (default), `idle` (`data-client-timeout`), `visible` (`data-client-root-margin`) or `media` (`data-client-media`). The island's default export gets the element and the parsed props, once; then the element gets `data-island-ready`.
- `@dustinedwards/devkit/vite/dev-toolbar`: `devToolbar()`, Astro's dev toolbar, in `vite dev` only. Inspect outlines the page's islands with their directive, props and whether they started. Audit runs axe-core (the site's own, served at `/@devkit/axe.js`; without it only performance is checked) and Astro's performance rules: a large image with no srcset, lazy above the fold, eager below it, a GIF over 100 KB, an island slow to start. Settings places the bar and hides it. siteScript already includes it; a React Router site adds `{import.meta.env.DEV && <script type="module" src="/@devkit/toolbar.js" />}` to its root.

An entry point is added when a repository adopts it. A release is the merge of a version bump in `package.json` and `CHANGELOG.md` (`release-self.yml` tags it); a consumer moves to it in its own pull request.
